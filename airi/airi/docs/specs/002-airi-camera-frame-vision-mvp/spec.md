# Summary

本规格定义 AIRI 摄像头抓帧视觉 MVP 的最小闭环：

- 用户显式开启摄像头预览
- 系统以前台可见、可停止、可节流的方式抓取静态帧
- 抓取结果复用现有图片附件链路进入聊天上下文
- Web 与 Desktop 共享同一套视觉状态语义、交互入口与降级规则

该 MVP 的目标不是“实时视频理解平台”，而是先把“摄像头帧 = 一种受控图片输入”做成稳定产品能力。

# Background

当前仓库已经具备三块相关基础：

- `packages/stage-pages/src/pages/settings/modules/vision.vue` 已把视觉能力分为图片输入、Bridge 多模态、实时摄像头视觉三档，但实时摄像头仍默认关闭
- `packages/stage-layouts/src/components/Widgets/ChatArea.vue` 已支持本地图片附件进入现有聊天输入链路
- `apps/stage-web/src/pages/devtools/model-driver-mediapipe.vue` 与 `packages/model-driver-mediapipe` 已证明浏览器摄像头取帧与逐帧处理在当前仓库中可行

但当前仍存在明显断层：

- 产品主链没有可复用的摄像头运行时抽象，摄像头逻辑仍停留在 devtools 试验页
- 聊天主链只认识“本地图片附件”，不认识“持续抓帧会话”
- 视觉设置页已暴露能力心智，但没有对应的执行路径
- 如果直接把实时视频推理接进主链，会引入权限、性能、隐私提示、消息膨胀与跨端适配等一系列一次性复杂度

因此需要先定义一个严格受控的 MVP，把连续视频问题降维为“按策略抓取静态帧并复用图片输入”。

# Goals

- 建立摄像头抓帧视觉的共享语义与最小能力边界
- 复用现有图片附件与多模态输入链路，避免重做 provider 协议
- 让 Web 与 Desktop 都能以显式授权、前台可见、用户可停止的方式使用摄像头抓帧
- 将 devtools 中已验证的摄像头取帧能力沉淀为共享运行时而不是页面实验代码
- 为后续升级为低频连续理解、感知驱动或桌宠视觉输入保留扩展点

# Non-goals

- 本阶段不做无限时长后台采集
- 本阶段不做原始视频流直接喂给模型
- 本阶段不做多摄像头并发或多人视觉
- 本阶段不做视觉记忆长期存档与自动回放
- 本阶段不把 `model-driver-mediapipe` 与聊天视觉输入强耦合
- 本阶段不新增 provider 私有协议来描述“视频消息”

# Proposal

## 核心产品语义

摄像头抓帧视觉 MVP 采用“显式会话 + 静态快照”的产品模型：

- 用户主动开始摄像头会话
- 界面持续显示预览与录入状态
- 用户可手动抓拍，后续可选开启低频自动抓帧
- 每一帧在进入聊天前都被标准化为现有图片附件对象
- 用户发送消息时，模型看到的是图片，而不是视频流

这意味着摄像头只是图片输入的一种来源，而不是一套独立的消息协议。

## 分层模型

在 `001-airi-web-desktop-parity` 已定义的 Shared Core / Runtime Adapters / Shell Apps 框架下，本能力落为：

- Shared Core
  - 摄像头会话状态机
  - 抓帧策略与节流规则
  - 预览面板与聊天附件装配逻辑
  - 错误、权限、隐私提示语义
- Runtime Adapters
  - Web camera adapter：封装 `getUserMedia`、设备枚举、帧抓取与资源释放
  - Desktop renderer adapter：优先复用浏览器媒体 API，后续允许接入桌面特有源
- Shell Apps
  - `apps/stage-web`
  - `apps/stage-tamagotchi`

## 能力契约

本规格不额外发明一套平行能力体系，而是在既有 `MediaCapability` 方向下冻结 `cameraFrame` 子契约：

- `checkAvailability()`
- `requestPermission()`
- `listDevices()`
- `startPreview(deviceId?)`
- `stopPreview()`
- `captureFrame(options?)`
- `getSessionState()`

共享层只关心：

- 当前端是否支持摄像头抓帧
- 权限是否已授权、被拒绝或需要再次请求
- 当前是否处于预览中
- 这次抓到的帧能否被转成标准图片附件

## MVP 交互范围

MVP 只覆盖以下产品路径：

- 在视觉设置页看到摄像头能力状态、隐私说明与可用性
- 在聊天输入区打开摄像头面板
- 看到当前摄像头预览
- 手动抓拍一张图片并作为附件加入待发送列表
- 可选开启低频自动抓帧，让最近 1 张抓拍结果持续替换“待发送快照”
- 发送消息后按策略清理或保留当前快照

其中“低频自动抓帧”必须满足：

- 默认关闭
- 只在预览面板处于前台可见时运行
- 只保留有限数量快照，MVP 默认最多 1 张
- 抓帧频率受严格上限约束，避免把 UI 变成视频转码器

## 状态机

共享层统一采用以下状态：

- `idle`：未申请或未启动会话
- `requesting-permission`：正在申请权限
- `previewing`：摄像头预览已开启
- `capturing`：正在抓拍单帧
- `denied`：权限被拒绝
- `error`：设备不可用、被占用或抓帧失败

状态变化必须对 Web/Desktop 呈现一致语义，不能让 UI 依赖端特有错误文案。

# Design Details

## 复用现有图片附件链路

当前聊天主链已经能接收本地图片附件，因此摄像头抓帧必须直接产出与现有图片上传一致的数据结构：

- `type: 'image'`
- `mimeType`
- `data`（base64 或等价序列化结果）
- `name`

这样做的收益是：

- 不修改 provider 主体协议
- 不新增视频消息类型
- 现有聊天发送、消息上下文与多模态链路天然复用
- 视觉 MVP 的复杂度被压缩在输入侧，而不是扩散到整个消息系统

## 摄像头会话 Store / Composable

需要新增共享摄像头会话层，统一承担：

- 当前会话状态
- 当前设备信息
- 当前预览流引用
- 最近一次抓帧结果
- 自动抓帧开关与节流配置
- 资源释放与生命周期回收

其 owner 应位于 Shared Core，而不是直接散落在 `ChatArea.vue` 页面级组件中。

## UI 装配原则

主链 UI 只增加最小必要表面：

- 设置页：展示可用性、权限状态、隐私说明、MVP 能力边界
- 聊天输入区：增加摄像头入口按钮
- 附件区：把抓拍结果与普通图片附件统一展示
- 预览面板：显示设备状态、抓拍按钮、自动抓帧开关、显式停止按钮

禁止在 MVP 阶段引入：

- 复杂时间线
- 视频剪辑式回看
- 自动长期存档
- 多帧同时送模的复杂编排

## 与 MediaPipe Workshop 的关系

`model-driver-mediapipe` 与 devtools workshop 证明了“摄像头帧 -> 逐帧处理”的技术可行性，但它不是产品主链的直接实现：

- workshop 当前把设备权限、渲染循环、错误处理、页面状态写在单页内部
- workshop 面向运动感知与模型驱动，不等于聊天视觉输入
- 本 MVP 只复用其中“安全获取帧源、可停止、可观测”的工程经验

后续如果要把视觉感知结果接给角色动作或环境理解，应以能力复用方式对接，而不是把 workshop 页面直接提升为主链实现。

## 隐私与资源策略

摄像头抓帧必须遵守以下硬约束：

- 默认关闭
- 只有前台显式操作才可开启
- UI 必须持续可见地展示“正在预览/正在抓帧”
- 切换路由、关闭面板、发送完成或端能力失效时，必须明确释放流资源
- 不在后台持续缓存帧
- 不隐式上传未经用户触发的快照

## 跨端语义

Web 与 Desktop 在 MVP 阶段都优先走浏览器媒体能力，但仍要保留壳层差异入口：

- Web：按标准浏览器权限模型工作
- Desktop：先与 Web 保持同语义，后续可以扩展本地摄像头选择、桌宠视觉输入或系统级源管理

共享层不能因为 Desktop 可扩展，就提前写入桌面特权逻辑。

# Verify & Test

完成后必须验证：

- 设置页能正确展示摄像头抓帧 capability 的可用性与权限状态
- 聊天输入区抓拍的图片能够复用现有图片附件链路发送
- 不支持或被拒绝权限时，Web/Desktop 都有一致的降级提示
- 关闭预览、切换页面或报错后，媒体流都会被释放
- 自动抓帧不会在后台持续运行，且不会无限累积附件
- 主链实现不依赖 devtools 页面本身

# Milestones

## M1 语义冻结

- 冻结 camera-frame MVP 的产品边界
- 冻结 `MediaCapability.cameraFrame` 子契约
- 冻结手动抓拍与低频自动抓帧的状态机和隐私约束

## M2 运行时沉淀

- 从试验页经验中抽出共享 camera runtime adapter
- 建立共享摄像头会话 store / composable
- 跑通 Web/Desktop 的预览、抓帧、释放闭环

## M3 主链接入

- 在设置页展示真实状态
- 在聊天输入区接入摄像头入口与预览面板
- 将抓拍结果接入现有图片附件发送链路

## M4 治理与扩展点

- 补齐权限失败、设备忙、不可用等异常语义
- 建立抓帧节流、生命周期释放与 smoke 检查
- 为后续多帧理解、视觉感知或桌宠视觉输入保留稳定扩展点

# Success Metrics

- 实时摄像头视觉从“文案占位”升级为可交付的主链 MVP
- 摄像头抓拍不要求改造 provider 消息协议
- Web/Desktop 共用同一套摄像头状态语义与附件装配逻辑
- 摄像头逻辑不再只存在于 devtools 页面
- 后续扩展视觉能力时，可以继续复用 camera-frame 能力与图片附件链路
